# Feature Specification: 急停清空 Console 日志（急停清场）

**Feature Branch**: `002-panic-clear-console`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "按下急停后清空日志：用户触发急停（快捷键或菜单）后，除停止全部输出外，同时清空 Console 的全部日志（消除摸鱼痕迹）。普通停止/暂停/完结不触发清空，仅急停触发。清空失败时静默降级（急停本身必须仍然生效）。"

## Clarifications

### Session 2026-10-11

- Q: 急停清空 Console 需要提供设置开关吗，还是急停必清、不可关闭？ → A: 设置窗口加开关，默认开；关闭后急停仅停止输出、不清空
- Q: 清理范围是 Console 全部内容还是仅本插件产生的行？ → A: 仅移除本插件产生的行（统一标记的连载行/完结提示与 [LogReader] 系统日志），业务日志原样保留

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 急停即清场 (Priority: P1)

摸鱼输出进行中，老板突然走来，用户按下急停快捷键：小说行立即停住，同时
Console 被整体清空——屏幕上不再残留任何"日志"，摸鱼痕迹完全消失。事后回
来，阅读进度还在，从断点继续读即可。

**Why this priority**: 急停是摸鱼的安全底线（宪法原则 II），而"停了但屏幕
上还挂着小说行"会让急停形同虚设；清空是急停语义的补完，唯一故事即全部价值。

**Independent Test**: Console 预置一条业务日志后开启摸鱼输出数行，触发急停
（快捷键或菜单各验一次）——小说行消失、业务日志原样保留；普通停止/暂停下
Console 内容不变；关闭"急停时清空"开关后急停只停不清。

**Acceptance Scenarios**:

1. **Given** 摸鱼模式输出中（Console 混有小说行与业务日志）, **When** 用户
   触发急停（快捷键）, **Then** 输出立即停止，且本插件产生的条目（小说行、
   完结提示、系统日志）被移除，业务日志内容与相对顺序原样保留。
2. **Given** 摸鱼模式输出中, **When** 用户通过菜单触发急停, **Then** 效果
   与快捷键急停一致（停止 + 选择性移除插件行）。
3. **Given** 摸鱼模式暂停中（Console 仍残留此前输出行）, **When** 用户触发
   急停, **Then** 残留的插件行同样被移除（清场不依赖引擎是否仍在输出）。
4. **Given** 摸鱼模式输出中, **When** 用户执行普通停止、暂停或自然完结,
   **Then** Console 内容保持不变（仅急停清场）。
5. **Given** 急停清场已发生, **When** 用户重新开启摸鱼模式, **Then** 从
   上次停止行的下一行继续输出（清空日志不影响阅读进度与配置）。
6. **Given** "急停时清空"开关已关闭, **When** 用户触发急停, **Then**
   输出立即停止，Console 内容保持不变。

---

### Edge Cases

- Console 里混有真实业务日志/报错时急停会怎样？（业务条目内容与相对顺序
  原样保留，仅插件行被移除——FR-002 修订）
- 保留条目的调试信息（调用堆栈展开、时间戳）会怎样？（选择性移除经"快照
  →清表→回灌"实现，保留条目仅保内容/类型/相对顺序，堆栈展开与时间戳
  丢失——已知代价，记入 Assumptions）
- 业务日志恰好包含标记 token（如字面 "[nv]"）时会怎样？（会被误判为插件行
  一并移除；标记可自定义，建议避开易碰撞的短词——已知边界）
- Console 已设过滤文本时急停会怎样？（过滤态下日志表的读取/清理范围不可
  靠，清理静默跳过——显示层本就已被过滤隐藏，不动任何条目）
- 清理入口在当前 Unity 版本不可用（内部 API 变动、反射失败）时怎样？（静默
  跳过清理，急停停止输出照常生效，不弹窗、不向 Console 写错误——错误日志
  本身也会暴露插件；MUST NOT 回退为全量清空误删业务日志）
- 引擎空闲（从未开启或已停止）时按下急停快捷键会怎样？（开关开启时同样
  执行清理——屏幕上可能仍残留之前读过的行；开关关闭时仅无输出可停）
- 清理与停止输出的先后与耗时关系？（先停后清、同一拍完成，清理 MUST NOT
  使急停的停止动作变慢或失败）
- 播放模式切换 / 域重载引发的静默停止会怎样？（那是安全停机而非急停，
  MUST NOT 触发清理）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 急停触发（快捷键或菜单入口）后，系统 MUST 在急停同拍停止全部
  输出；当"急停时清空"开关开启（默认）时，MUST 在 1 秒内移除 Console 中
  本插件产生的全部条目。
- **FR-002**: 清理为选择性移除：MUST 仅移除本插件产生的条目（携带统一标记
  的连载行与完结提示、"[LogReader]" 前缀的系统日志）；非本插件日志 MUST
  原样保留（内容与相对顺序不变）。
- **FR-003**: 非急停路径——普通停止、暂停、恢复、自然完结，以及播放模式
  切换 / 域重载引发的静默停止——MUST NOT 触发清理。
- **FR-004**: 清理动作失败或不可用时 MUST 静默降级：不弹窗、不向 Console
  输出任何错误提示，且 MUST NOT 回退为全量清空（宁可不清理，也不误删业务
  日志）；急停的停止输出能力 MUST 不受影响。
- **FR-005**: 清理 MUST NOT 影响阅读进度、书架与用户配置。
- **FR-006**: 引擎空闲状态下触发急停入口，开关开启时 MUST 同样执行清理
  （清场语义不依赖引擎状态）。
- **FR-007**: "急停时清空 Console"MUST 作为设置项在设置窗口提供，默认开启
  并持久化（重启编辑器后保持用户选择）；关闭后急停仅停止输出、不清理
  Console。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: "急停时清空"开关开启（默认）时，触发急停后 1 秒内 Console 中
  本插件条目数为 0。
- **SC-002**: 开关开启时，急停后非本插件日志保持率 100%（内容与相对顺序
  不变）。
- **SC-003**: 普通停止 / 暂停 / 完结场景下，Console 既有内容保持率 100%。
- **SC-004**: 清理能力失效的降级场景中，急停停止输出的成功率为 100%，非
  插件日志保持率 100%，且 Console 不新增任何插件相关日志。
- **SC-005**: 急停清场后再次开启，续读位置与急停前停止位置偏差为 0 行。
- **SC-006**: "急停时清空"开关状态在编辑器重启后与重启前完全一致。

## Assumptions

- "本插件产生的条目"识别规则：消息含 `[<统一标记>]`（内置预设均以方括号
  token 嵌入标记，如 `[NetModule][nv]`）或以 `[LogReader]` 开头（插件系统
  日志）。默认标记 `nv` 较短，业务日志含字面 "[nv]" 会被误移除——可通过
  自定义标记规避（已知边界，见 Edge Cases）。
- 选择性移除的实现代价：保留条目仅保内容、日志类型与相对顺序，调用堆栈
  展开与时间戳不保真（编辑器日志表的按条移除需要"快照→清表→回灌"）。
  紧急场景下"内容保留"优先于"调试元信息完整"。
- "痕迹"仅指 Console 可见内容；进度文件、设置与书架均为本机文件且不在
  Console 展示，不属于清场范围（Boss 走后需能继续读）。
- 本功能为 001 急停行为的增强，不改变急停的触发入口与停止语义。
